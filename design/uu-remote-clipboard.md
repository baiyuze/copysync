# UU 远程剪贴板占位文件循环 — 1.3.2

## 现象与证据

2026-10-10 用户反馈：Windows 复制文件，在 UU 远程开启时，Mac 复制记录每秒新增 `.uuremote_aeawv` 加数字的文件。截图涵盖 1.1 GB 安装包、5.1 KB 源码和 810 KB 压缩包，不能据此归因于大文件阈值。

只读检查本机 CopySync 数据库，发现 92 条匹配项；最近样本的源路径位于 `~/Library/Application Support/com.netease.uuremote.server/Clipboard/`。仍存在的样本为 0 字节普通文件，其余部分已经被移走或删除。未读取用户文件内容。

旧实现只对自己写入时的剪贴板变更计数去重。UU 再次写入新的占位路径后，计数变化，CopySync 会扫描、生成新 ID、入库并向配对端发送；0 字节记录满足自动推送条件。这解释了记录增长以及两套剪贴板同步共同作用时的循环入口。这里没有读取或解析 UU 的 UDP 流量。

50 MB 只控制 `WillPush`，不是允许进入复制记录的大小上限。超过阈值的真实文件应只公告元数据，按需拉取。UDP P2P 设置不需要改动。

## 修复边界

- 在本机内容入库之前按文件名匹配 `.uuremote_aeawv` 加非空 ASCII 数字后缀，排除后再扫描和发送。纯占位选择安静跳过，混合选择保留正常文件。匹配同时支持 Windows 与 macOS 路径。
- 不按空文件、隐藏属性、临时目录或 UU 整个应用目录粗略排除；其他相似文件名（如 `.uuremote_aeawv123.backup`）保留。
- 接收旧版客户端的纯占位 offer 时不入库，不发布 UI 事件。未被接纳的传输头不创建接收器、不分配缓存目录。
- 打开历史数据库时删除所有文件条目均匹配该命名的文件记录，级联清理其条目。普通记录、无条目记录、混合选择保留。只删除记录；UU 的源文件不动，CopySync 的孤儿缓存由现有 GC 回收。
- 两端都应升级。未知占位命名和其他软件对普通内容的重复同步不在本次精确过滤范围内；必要时只保留一个工具负责剪贴板同步。

设备间协议没有变化，服务器无需升级。macOS/Windows 客户端版本为 1.3.2。

## 回归验证

- 100 次不同名字的本机占位文件复制：0 条记录。
- 100 个旧版纯占位 offer 及紧随的传输头：0 条记录、0 个 UI 事件、0 个接收器。
- 混合选择中仅保留真实文件；普通隐藏文件和空文件正常记录。
- 5 KB、50 MiB、50 MiB + 1 字节、1100 MiB 的真实文件保持正确总大小与自动推送判断。大文件使用稀疏文件验证元数据分流，不代表已实传 1 GB。
- 升级清理覆盖本机/远端、多个占位、正反顺序的混合选择、近似名字、普通空文件、非文件记录、无条目记录；重复启动结果一致，UU 源文件仍存在。
- 本机 client-core 与 server 的完整 `go test ./...`、`go vet ./...`，以及过滤/存储/同步包的 `go test -race` 已通过。Flutter 分析与 46 项测试通过。
- 使用 Go overlay 临时移除源头过滤，对照运行 `TestRemotePlaceholderFlood`，第一条占位文件即被错误入库，测试按预期失败；启用修复后通过。

本轮没有操控真实 UU 远程会话重现完整交互，因此不把自动化回归描述为 UU 实机端到端验证。正式复测时保持 UU 开启，分别复制小文件和超过 50 MB 的文件，确认只新增真实文件记录、不随时间增长，且正常文件可传输与粘贴。
